# 站间协作（peer）

两台中转站之间怎么互相用：**配对 → 只读取数 → 字节直通**。三条独立开关，都能单独关掉。

> 一句话原则：**信任靠配对建立，转发靠普通渠道，直通只是省一次解析。**
> 任何"因为双方可信就放宽规则"的做法都不要做。

---

## 1. 配对

双方各存一个令牌，一次带外交换（聊天、邮件、扫码都行），写进 `<home>/peers.json`：

```json
{
  "peers": {
    "lab": { "url": "https://lab.example.com", "token": "rhp_xxx", "enabled": true, "note": "朋友站" }
  }
}
```

- `peer_id` 只是本地别名，不参与鉴权；
- 令牌用 `rhp_` 前缀，`peer.new_token()` 生成；
- 停用（`enabled: false`）与不存在给同一个回答——不告诉探测方"这个站存在但被停了"。

**为什么不做请求签名**：两站之间走 HTTPS，传输完整性由 TLS 负责。加 HMAC + 时间戳
只是多一类"时钟偏差导致 401"的运维问题，换不来真实安全性。真要"不可否认的对账凭证"，
那是另一个场景（导出快照给第三方核算），到时候再加。

## 2. 只读端点（取余额 / 价格 / 站点信息）

```
GET /v1/_peer/info     站点名、版本、能力、模型数
GET /v1/_peer/balance  可用额度（-1 = 未知）
GET /v1/_peer/pricing  每模型单价（元/百万 token，含峰谷倍率）
Authorization: Bearer <对方给我的配对令牌>
```

未配置任何 peer 时，这三个路径与 404 等价。

**所有应答都带警告字段，且必须原样展示给使用者：**

```json
{ "ok": true, "advisory": true, "source": "peer",
  "warning": "数据由上游自报，可能被修改或延迟更新；仅供展示与告警，不作为结算、对账或退款依据（结算以本站请求日志为准）" }
```

理由：余额/价格本来就是**上游自报**。公开接口（`/v1/dashboard/billing/*`）能给同样的数，
但那份数一样不可信——上游可以改、可以延迟、可以按渠道给不同结果。

**结算永远以你自己的请求日志为准**，对端余额只回答一个问题：还要不要继续给它派流量。

`balance` 里 `remaining = -1` 表示"不知道"，不是"没钱"。渠道未上报额度时必须报 -1，
报 0 会让人误以为该充值。

## 3. 字节直通

```
POST /v1/_peer/forward
Authorization: Bearer <配对令牌>
X-Peer-Path: <下游要求的那个路径>
（body 原样透传，≤ 2MB）
```

允许的路径（正则白名单，不做通用代理）：

| 路径 | 方言 |
|---|---|
| `^/v1/chat/completions$` | OpenAI Chat |
| `^/v1/messages$` | Anthropic Messages |
| `^/v1/responses$` | OpenAI Responses |
| `^/v1beta/models/{model}:(generateContent|streamGenerateContent)$` | Google Gemini |

Gemini 的模型名编码在路径里，所以不能像其它三种映射成固定字符串——校验形状后原样转发。

出口站把 body 原样交给**自己的公开接口**（loopback），再把响应字节原样回传。
它省掉的是「入口站 → 出口站」这一跳的解析与重组。

三条硬约束：

1. **不做通用代理**：只认上面三种方言，路径写死，不接受自定义 path/host；
2. **规则照常生效**：loopback 调的是本站公开接口，令牌、额度、IP 白名单、RPM、
   模型限制一个都不少——直通省的是 CPU，不是规则；
3. **没有主凭证就拒绝**：本站未配置 `--api-key` 时返回 503，不在直通路径上开免鉴权后门。

### 谁能用直连（必须站长授权）

直连会跳过本站对请求的解析，因此**不能由用户自助开启**：

```
管理面 发放/编辑令牌 → ☑ 允许直连（危险）
```

- 默认 **False**。未授权的下游令牌命中直连模型时返回 403：
  「该模型只提供站间直连通道，需要站长在本令牌上开启「允许直连」」；
- 面板自助建令牌时这个字段被忽略（用户永远不能给自己开）；
- master 凭证视为站长本人，不受此限；
- 每次拒绝写审计 `peer.relay.denied`（令牌名、模型、来源 IP）。

为什么不"悄悄降级到普通渠道"：那会让用户以为自己在走普通通道，
而实际请求去了哪里、花了多少钱都变得难以解释。明确拒绝比默默改道更安全。

### 入口站怎么配

直通在入口站是一条**上游渠道**（协议名 `relayhub-passthrough`），不是全局开关：

```json
{
  "key_id": "lab-direct",
  "label": "lab 直通",
  "protocol": "relayhub-passthrough",
  "base_url": "https://lab.example.com",
  "api_key": "对方给我的 rhp_ 配对令牌",
  "models": ["deepseek-v4-flash"]
}
```

- 命中该模型时，入口站**不解析、不翻译**，把客户端原始字节转发到对方的
  `/v1/_peer/forward`，响应字节原样回给客户端；
- 没命中就走普通渠道，两条链路互不影响；
- `model_mapping` 在直通下**不生效**（原始字节不重写），需要映射就别用直通。

**记账口径**：直通**照常扣费**，只是用量来源分两级——

1. 先从响应尾部嗅真实 usage（OpenAI 的 `prompt/completion_tokens`、
   Anthropic 的 `input/output_tokens`、Gemini 的 `prompt/candidatesTokenCount`）；
2. 嗅不到就按字节估算（4 字节 ≈ 1 token）。

两级都不依赖解析整个流，所以直通仍然零翻译。对账精度以出口站日志为准，
但下游令牌的额度、RPM、模型限制全部照常生效。

### 什么时候值得开

- 链路 ≥2 跳，且客户端方言与出口站上游方言**一致**（此时才是真正的零翻译）；
- 方言不一致时，出口站仍要翻译，直通的收益只剩"入口站不做一遍"，收益变小但仍为正。

### 什么时候别开

- 只有一跳：直接给对方发一个下游令牌，把对方配成普通上游渠道更简单；
- 对方不完全可信：直通会把你的请求体原样送到对端。

## 4. 把对端当普通上游（推荐的第一步）

不需要任何站间接口，只要有对方给的一个令牌：

```json
{
  "key_id": "friend-station",
  "label": "朋友站",
  "protocol": "openai-chat",
  "base_url": "https://friend.example.com",
  "api_key": "对方给我的 rht_ 令牌",
  "models": ["deepseek-v4-flash"]
}
```

冷却、重试、记账、限流、语义缓存全部继承，零新代码。
**只有当这一跳的解析开销确实成为瓶颈时，才值得开直通。**

## 5. 滥用面（开源后被照抄，必须写出来）

| 风险 | 这里的处理 |
|---|---|
| 被当免费中转 | 必须持有配对令牌；令牌可以随时在 `peers.json` 里停用 |
| SSRF | 不接受任何目标地址，loopback 只打自己 |
| 绕过计费/限流 | loopback 走公开接口，规则全量生效 |
| 请求体放大 | 上限 2MB，超限 413，不缓冲 |
| 匿名跳板 | 审计记 `peer.forward`（谁→谁、方言、字节数、状态） |

启用直通即意味着：**你的站点可以被配对方当作出口使用，流量与内容责任在你这边。**
仅在双方互信的小范围启用。
